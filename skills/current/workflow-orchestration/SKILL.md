# ASES workflow orchestration

Inspect current evidence and identify the smallest unresolved question. Choose targeted recon when the mechanism is unknown; independent parallel tests for separable hypotheses; synthesis for conflicts; implementation when requirements are sufficiently settled; and verification against observable claims. Do not require a ritual sequence or create agents to increase agent count.

**Experiments and scope expansion:** Apply the [canonical experiment and decision admission procedure](../../../docs/methodology/ASES%20Task-Scoped%20Information%20and%20Handoff%20Method.md#experiment-and-decision-admission) before launching a new investigation: establish the parent decision, qualify necessity from existing evidence, freeze the bounded registration, classify independent review need and obtain exact-revision authority. Routine verification and already admitted matrix slots inherit existing approval; stop or transfer when the decision is resolved. Do not turn this into a new per-test review or mandatory form.

Choose execution environment according to task: bounded GitHub Actions work units, Codespaces/Modal for longer exploratory work when available and authorized. Parallelize only separable questions; sequence dependent work. Isolate shared files, worktrees, databases, browser/session identities, deployed resources and provider quotas, or sequence the checks when isolation is unavailable. Compare results with acceptance and distinguish observed, inferred, contradicted and not-tested claims; route only the remaining blocker to the next mode. Apply the [canonical destination-first handoff method](../../../docs/methodology/ASES%20Task-Scoped%20Information%20and%20Handoff%20Method.md#destination-first-execution-and-recovery): establish final artifact home/status and disposable workspace before work, push and verify short recoverable checkpoints during development-agent execution (approximately five minutes or meaningful transitions), update relevant authoritative sources each substantive Chat coordination turn instead of using a timed commit cadence, and verify retained useful results on the appropriate repository's main branch separately from disposable branch progress. Persist verified test evidence and work-unit position; investigate stale progress with corroborating signals rather than killing a healthy worker solely for unchanged terminal text.

**ChatGPT mode selection:** Stay in Chat unless the operator explicitly requests Work mode. Do not proactively suggest or initiate a mode switch for long, complex or connector-based work. Continue using authorized Chat tools; report concrete unavailable capabilities instead. See the canonical task-scoped method for the operator preference and rationale.

**Ordinary Chat coordination and discussion:** Before concluding a substantive turn, identify the material changes and resolve existing records by subject and information ownership. Apply the [canonical Chat persistence and record granularity rules](../../../docs/methodology/ASES%20Task-Scoped%20Information%20and%20Handoff%20Method.md#chat-persistence-and-record-granularity): Projektor for intent, decisions and evolving questions; repository for durable artifacts, findings and evidence; Work Notes for operational progress, blockers and resume pointers. Reuse records across conversations; replace stale checkpoints, use targeted patches or concise comments where appropriate, and avoid duplicate narratives or artificial writes. Verify complete retrieval before replacing a body, use revision-aware mutations where supported, read back material writes and report any missing durability explicitly. Discussion capture is not execution authorization. Do not impose the ASES lifecycle on other projects; resolve their applicable conventions. This is a model-followed procedure, not a platform hook.

**Model feedback:** Apply [per-turn capability evidence intake](../../../docs/methodology/ASES%20Task-Scoped%20Information%20and%20Handoff%20Method.md#model-capability-evidence-intake) whenever new material model feedback arrives, including operator corrections, results, failures and usage. Verify registry intake or preserve a pending receipt before concluding; do not wait for session closeout.

**Material related work:** Apply the [canonical cross-chat related-work flag procedure](../../../docs/methodology/ASES%20Task-Scoped%20Information%20and%20Handoff%20Method.md#cross-chat-related-work-flags) when findings materially affect another active checkpoint, and consult relevant flags encountered during ordinary recovery before advancing the affected question.

**When drafting an autonomous-run or multi-agent launch brief, read `skills/current/compact-prompt/SKILL.md` first and apply its source-admission gate.** An orchestration assignment is not automatically a frozen build packet: when a delegated work unit is a substantial bounded implementation, additionally read `skills/current/compile-build/SKILL.md` and the active canonical `docs/methodology/ASES Bounded Project Build Method.md` for that work unit. Do not load superseded prompt skills merely because an older PR cites them. Before actual model dispatch use `skills/current/agent-launch/SKILL.md`; for independent reviews use `skills/current/review-launch/SKILL.md`. Route decisions and operational checkpoints to their respective authoritative destinations; don't reconstruct settled meaning from obsolete Crosslink/VPS runbooks. End with a verified result or a specific blocker.

**Recover from routine run failures within the turn.** Inspect failed execution evidence, identify the cause or cheapest discriminator, and when feasible correct and rerun within the existing authorized scope before returning. Do not stop solely to report a recoverable test, harness, dependency, or transport failure. Use bounded retries with evidence of progress; preserve red evidence, do not weaken acceptance criteria, conceal material failures, broaden permissions or budgets, or silently change the implementation under test. Escalate when a human decision, new authority, unavailable capability, material scope change, or unresolved blocker prevents useful further progress. If a verified execution is still running or turn limits prevent completion, record its exact resume point and state the actual status. Distinguish routine recovery from a substantive finding that changes the decision.
