## What was wrong (root-cause analysis)

The crosslink-guard plugin's health check (`checkCrosslinkHealth`,
`.opencode/plugins/crosslink-guard.ts`) treated a failed
`crosslink --version` subprocess probe as "Crosslink unavailable" and
HALT-blocked **every** bash/write/edit call in the worktree.

### Evidence gathered (evidence-based; from /tmp/crosslink-guard.log,
opencode.log, and filesystem inspection)

1. **The failure is intermittent per-spawn, not a static outage.** Guard log
   2026-08-30: worktree `pp3g-yBYs-...` failed the probe at 20:55:09 and the
   SAME process passed it at 20:55:16 (bash blocked, then edits allowed).
   Meanwhile worktree `stop-button` passed consistently at the same times.
2. **It is not command-not-found.** Bun shell exits **127** for
   command-not-found (verified against Bun's documented/reported behaviour);
   the observed failure is `exit=1 out=` — the binary was found and ran.
3. **The binary cannot legitimately exit 1 on `--version`.** The only
   crosslink on the box is `/home/claude-code/.cargo/bin/crosslink` (real
   Rust/clap binary; `main()` calls `Cli::parse()` first, clap handles
   `--version` before any logic — verified in the fork source at
   `/home/claude-code/projects/crosslink/crosslink/src/main.rs:2749,89`).
   So the exit=1 originates in the spawn/execution layer of the sandboxed
   launch environment, not in PATH resolution and not in the CLI itself.
4. **The HALT was self-defeating.** It blocked ALL bash — including
   `crosslink sync` and the very `crosslink issue intervene` command the
   HALT message instructs the agent to run. A false-positive probe failure
   therefore permanently bricked the agent (this session included: every
   bash call in this session was blocked for its whole duration).

### WHY / WHAT / HOW CERTAIN / WHAT-NOT-TESTED

- **WHY**: the health check conflated "probe failed" with "crosslink
  unavailable" — a category error. The authoritative availability signals
  are (a) an executable binary exists, (b) the issues.db is readable and
  queryable. The probe is only corroborating evidence.
- **WHAT**: guard-log timelines (fail→pass within 7s in one process;
  pass in sibling processes at the same moment), Bun shell exit-code
  semantics (127 ≠ 1), clap parse-order in the fork source.
- **HOW CERTAIN**: the failure classification and the fix direction are
  evidence-based. The precise kernel/runtime mechanism producing exit=1
  (spawn failure mode under the sandboxed launch chain) is **not identified**
  — see WHAT-NOT-TESTED.
- **WHAT-NOT-TESTED**: (1) the exact low-level mechanism of the exit=1
  (could not execute any diagnostic command — the bug being fixed blocked
  all bash in this session); (2) the fixed plugin has NOT been executed;
  (3) the updated cheapest-test script has NOT been run; (4) live
  post-restart behaviour NOT verified.

## The fix (implemented)

File: `.opencode/plugins/crosslink-guard.ts` (git-tracked; propagates via
branch merge). Three coordinated changes:

1. **`resolveCrosslinkBinary()`** (new): resolves the crosslink binary to an
   absolute path — `Bun.which("crosslink")` first (no subprocess), then
   known locations `~/.cargo/bin/crosslink` and `~/.local/bin/crosslink`
   (existence + executability checked). Cached per process. This removes
   the PATH-dependence that gives the issue its name ("sandbox PATH
   blocking worktrees"): a sandbox whose PATH lacks `~/.cargo/bin` now
   still finds the binary.
2. **`runCrosslink()`**: invokes the resolved absolute path instead of the
   bare `crosslink` name (falls back to the bare name only if resolution
   failed). ALL guard CLI interactions (health probe, kill/pause flags,
   active-issue gating) become PATH-independent.
3. **`checkCrosslinkHealth()`**:
   - Binary missing (not on PATH AND not at known locations) → **HALT
     unchanged** (genuine unavailability).
   - Probe fails with binary present → **one immediate retry** (300ms;
     catches sub-second transient spawn failures; explicitly NOT a
     wait-and-retry loop, preserving #514 doctrine).
   - Probe fails twice with binary present → **degrade to warning, not
     HALT**; the DB checks (issues.db exists/non-zero/queryable/lock-free —
     all unchanged hard gates) remain the authoritative verdict, and the
     `session status` probe (step 5) is skipped since the CLI is
     unresponsive in that moment. A real CLI *answer* carrying a hydration
     warning still HALTs (#514 semantics preserved where the CLI speaks).
   - HALT message step 6 updated to describe the new resolution order.

Also updated `scripts/guard-halt-cheapest-test.js` to mirror the new
decision matrix (binary-missing → blocked; probe-fail + DB-healthy →
tolerated; genuine DB/config faults → blocked) and to resolve paths
relative to the script's own repo root instead of the hardcoded
`guard-halt` worktree.
