# Resource Console v0.1 — IT3812 VPS Reconnaissance

## Executive result

**VPS isolated implementation test readiness: NO.** Access and read-only reconnaissance succeeded through the requested Windows OpenSSH alias. The host is Ubuntu 22.04.5 LTS with systemd 249, cgroup v2, Python 3, Node, SQLite 3 and `systemd-run`. However, the root filesystem is full (100%, about 504 MiB available), no reusable dashboard HTTP ingress or Cloudflare Access/tunnel path was verified, and the checked-in VPS ASES worktree is dirty and on a divergent `main`. The existing VPS worktree and active sessions were left untouched. The current capacity condition alone makes adding an isolated test artifact/process on-host an unsafe next step.

**Smallest viable mechanism, conditional on blockers clearing:** serve only the built static UI through an already-existing authenticated private HTTP route (none was established in this recon), and route explicit monitor-control requests to a **systemd user socket-activated service**. The socket can remain available while the application/collector is absent; first explicit Start activates the short-lived service. Have that service own a process group and renewable, per-tab leases, reap the collector on final Stop/lease expiry, and exit. Use the service's own heartbeat deadline as the abrupt-disconnect fallback; do not rely on browser unload. This is a design recommendation, not a tested mechanism. No unit or socket was created.

Socket activation is technically available as a systemd facility, but it is not yet an implementation selection: there is no verified private proxy route to it, no authenticated origin-to-socket authorization proof, and no isolated lifecycle test. If user-systemd socket forwarding through the verified ingress cannot be secured, the next-smallest alternative is an authenticated transient user service spawned only by a specific Start endpoint, with a short lease watchdog; it still requires a verified static ingress and safe authenticated trigger.

### On-demand session mechanism

The design requires no collector on page GET, Start-only activation, multi-tab leases, clean stop under final close and hard expiry within 30 seconds after last heartbeat. The host confirms enough systemd facilities to attempt an isolated test later, but does not prove the security or shutdown contract.

Recommended smallest candidate:

1. Keep UI assets static and served by an already verified private ingress. Static asset GETs have no collector side effect.
2. Put only the monitor control/read API on a systemd **user** Unix socket. Restrict socket filesystem ownership/mode to `claude-code`; do not expose the socket directly to the browser or a public interface.
3. Let the authorized ingress make a narrowly scoped local proxy to the socket only after authenticating the caller and checking Origin/CSRF on Start/heartbeat/Stop. Keep any ingress-to-socket credential/identity server-side. A protected static site alone does not establish API authorization.
4. The socket activates one service instance on explicit Start. The service tracks idempotent lease IDs/generations, heartbeats, and last activity. It spawns collectors in an owned process group only while a valid lease exists, kills only that group after final release/expiry, closes SQLite, and exits. A short periodic timeout (e.g. 5 seconds) should enforce the ≤30-second abrupt-loss target. Repeated/stale heartbeats must not revive expired generations.
5. Keep the listening socket but no dashboard app/collector resident while inactive. Confirm that the systemd user manager remains available across logout/reboot under existing policy; do not change lingering as part of recon.

**Why not browser close alone:** mobile/browser crashes and network loss make unload delivery unreliable. Leases with server-side expiration are required even if normal close sends immediate Stop. **Why not a permanently running controller:** violates idle-zero application process objective. **Why not launch from every static/API GET:** page and history reads must not start telemetry; only an authenticated explicit Start can acquire a lease. **Why not assert socket activation already works:** no app socket exists and no isolated service test was performed.
