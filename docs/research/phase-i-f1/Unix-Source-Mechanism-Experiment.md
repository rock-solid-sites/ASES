# Unix descriptor transfer: preregistered mechanism experiment

Hypothesis: a request's current bearer value and connection-time `SO_PEERCRED` cannot distinguish the original connector from another process that later receives its connected descriptor via `SCM_RIGHTS`. A receiver with `SO_PASSCRED` enabled before connection should receive per-message `SCM_CREDENTIALS` distinguishing the original replacement sender from the recipient of the same descriptor. Predictions: (1) replacement sender's current request is received with its PID; (2) after transfer, old sender sends the identical current value over the same connection and `SO_PEERCRED` remains the replacement PID, while per-message PID is old; (3) a current-token-plus-connection-PID rule would admit both, and a current-token-plus-per-message-PID rule would admit replacement and refuse old. Observations and rule evaluation are kept separate.

Premises: local Linux Unix `SOCK_SEQPACKET`, the kernel's delivered ancillary credentials and `SO_PEERCRED` are trusted, same UID/GID but distinct live PIDs in one PID namespace; the child relation is verified while both are alive. The replacement's PID is pre-authorized by the supervising fixture, no process intentionally forges ancillary credentials, and no privileged adversary changes credentials or PID namespace. The fixed request value is a test stand-in for current bearer evidence, not a credential implementation. The server reads one message per record; timing and provenance of each receive are recorded. No production process, ingress, policy, storage, network, or capability isolation is changed. This tests a local mechanism; it is not F1 or F3 acceptance, a complete authentication design, or proof against privileged impersonation, process/PID reuse, namespace crossings, or compromised replacement.

Repository search at base `d227a22b`: `docs/research/kernel-0/kernel0_recovery_check.py` uses `SCM_RIGHTS` as a trusted supervisor attachment to a separate prototype, while no source-attribution receiver candidate was found in `docs/research/kernel-0`. This fixture does not claim to run that prototype. Closure's realization boundary already documents these OS semantics; this is a local discriminating observation, not a new upstream discovery. The 2026-11-02 proposals remain provisional.

## Observation and interpretation (2026-11-03)

Commands, from the repository root:

```sh
python3 -m py_compile docs/research/phase-i-f1/unix_source_mechanism.py
python3 docs/research/phase-i-f1/unix_source_mechanism.py > docs/research/phase-i-f1/Unix-Source-Mechanism-Output.json
```

Both exited 0. The output is preserved adjacent to this report. The script SHA-256 is `f7c19a599637f2866036bfbb067aa52a66589538235539239ce8b96ae155b374`; raw output SHA-256 is `16831d22009d5e4e1ae2004c04e2a6b43838f781accabebdd6e9b5d5b26f147f`. The kernel was Linux `6.18.57`, Python `3.12.14`. This is one local run; PID values are ephemeral.

The receiver enabled `SO_PASSCRED` on its listening socket before connection, accepted a single connection, and sampled `SO_PEERCRED` once. The replacement process (PID 3369) sent `current-evidence`, then transferred that connected socket using `SCM_RIGHTS` to the old process (PID 3370), which sent the identical bytes. The replacement waited so that both remained alive; `/proc/3370/stat` showed parent PID 3369. The receiver's connection peer was PID 3369 for the connection; its two delivered per-message credential PIDs were 3369 and 3370 respectively. Both messages and the peer had UID and GID 1000. Ancillary data and payload truncation were checked and absent. The child exited successfully.

The fixture evaluated two rules **after receipt**, not as production admission: current bytes plus connection peer PID accepted both messages; current bytes plus per-message PID accepted the replacement and rejected the old sender. Thus this run supplies a concrete counterexample to relying on a connection-time peer identity as the source of every request after descriptor delegation, and an authorized positive control for the per-message distinction. It does not show that a production protected effect was blocked, that a per-message PID is a durable identity, or that the replacement itself cannot proxy an old producer's request. The per-message result depends on the kernel and supervision premises above; source attribution of a direct sender is not necessarily attribution of the ultimate originator.

Next discriminator: in a separately scoped candidate ingress, have the old participant ask the authorized replacement to proxy the same request rather than transfer the descriptor. Determine whether the declared policy excludes the ultimate initiator and what trusted binding, if any, can distinguish that case. PID reuse, process exit/restart, namespace translation and privileged credential manipulation require further separately bounded tests before applying this mechanism to a real acceptance boundary. F1/F3 completion and independent review remain open.
