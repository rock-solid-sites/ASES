# Two-process SQLite capacity competition — preregistration

The F1 capacity-one graph assumes serialized single-unit reservation. The Kernel-0 persistent service holds an in-process lock around a current read/validate/write and uses one SQLite holder; its concurrent tests include exclusive grants but not two independent processes directly contending on a SQLite-backed reservation. The prior two-unit F1 experiment is an abstract interleaving, not a host transaction test. This small disposable bridge uses the same SQLite rollback-journal and synchronous FULL profile, without modifying the inherited service or asserting implementation refinement.

One database initially has no reservations or effects; exactly one resource unit and two named contenders. Separate subprocesses first announce readiness. Reference: both receive a start command, each executes `BEGIN IMMEDIATE`, reads the current reservation count inside that write transaction, and if empty inserts its own reservation and matching finite test-effect row in the same transaction; otherwise rollback and deny. SQLite serializes the two write transactions; expect exactly one committed winner and one denial. Detached-precheck mutant: both independently read zero outside any write transaction, then each announces this observation; supervisor releases neither until it has both reports. Each thereafter starts a write transaction and inserts its reservation and effect based on its stale precheck without a current recheck. Both should commit. The table deliberately has no uniqueness constraint, so the unsafe variant is not silently repaired by a schema invariant.

For both variants, successful writer reports `committed` only after `COMMIT` returns, then pauses awaiting supervisor permission to publish an `ack`. The supervisor independently opens the store after both decisions and before permitting any ACK, reads all reservation and effect rows and integrity; then permits ACK and confirms one-to-one correspondence of committed reports, pre-ACK durable rows, ACKs and effects. The observer computes count and owners directly from the database; it does not trust child results to decide conservation. Run an inherited F1 serial reservation positive/negative control for matching one-winner semantics. Compare only the declared finite outcome, not full refinement. Two fixed supervised schedules; process readiness, both mutant prechecks, decisions, pre-ACK observation, final ACKs and child exit statuses recorded. Explicit per-pipe/process deadlines, kill/reap on failure, temporary isolated databases, outer 30-second timeout. No exhaustive schedule search.

Premises: correct SQLite/VFS and Unix locks, one live host, trusted fixture setup, same database file, finite rows and atomic SQLite transactions; no hostile participants or bypass, no external effects beyond test rows, no independent resource-use enforcement, no power loss or killed writer during commit, no OS/storage failure, rollback adversary, client authentication, production service or general runtime. Concurrent invocation does not prove parallel execution; barriers force the mutant's stale-read ordering. Reference commits are atomic under SQLite's assumed contract; observed run does not prove it universally. C1/C3 and F1 are partial, F5 review remains open.
