# Same-object holder exclusion, retained lock reference, and pathname replacement

Executed preregistration99513e5 through the unchanged real SQLite holder service. Candidate wrapper acquires nonblocking flock before exposing the actual socket route; one context0 use lane, separate trusted management bootstrap lane. No Landlock or other unavailable enforcement retry.

Three fixed schedules:

* Ordinary same-inode guard: B refuses while A serves and while A is SIGSTOPped (stop observed with waitpid). Resumed A reads its prior ACKed content. After A SIGKILL/reap, B acquires the same inode, cold-reads exact accepted content, and ACKs a new value.
* Retained reference: A sends its lock FD with real SCM_RIGHTS to another direct supervisor child. After A is killed/reaped, B still refuses on the same inode. Descriptor keeper closes/reaps; B then acquires and recovers exact content. Reaped original holder alone does not prove all lock references disappeared. This is deliberate descriptor transfer, not spontaneous inheritance or a claim about arbitrary descendants.
* Changed lock object: fixture unlinks lock pathname while A retains old locked inode. B creates/locks a new inode and activates. Both actual services remain live and ACK supported writes. SQLite still serializes each state update; this is not database corruption or a transactional exclusivity failure. It demonstrates that one stable protected lock object is a necessary premise for this cooperative sole-holder mechanism. Trusted fixture pathname mutation is outside that premise.

Raw holds lock device/inode, nonblocking errno11 refusals/exit75, ready/kill/reap/FD events, real ACKs/cold state, executable/source hashes and invocation-base SHA. All successful holders exit-9 after explicit cleanup, keeper exits0; no orphan child created. No host-wide control, production, physical-source fencing, native Work Unit confinement, arbitrary credential revocation, distributed lease, power loss or F1/F3 closure.
