# Two-unit competing reservations — preregistration

The inherited `capacity-one` graph conserves one P-owned unit between sibling views, with serialized allocation and separate consumption. It does not model numeric requests or the check/commit interleaving between competing reservations (T04); the design's D-8 is a capacity-one abstraction, not evidence for arbitrary arithmetic. This separately bounded fixture extends that accounting idea without changing the F1 model or defining a runtime.

Hypothesis, fixed before execution: with parent capacity two and requests C=2 and S=1, both may prepare against the same initial available capacity, but a commit-time authoritative check admits at most one if their sum would exceed two. Bypassing that check after both prepares admits three reserved units and an independent ledger-sum observer detects over-reservation. A second case C=1/S=1 must admit both and permit each to consume one; C consumption before its own commit, repeated consumption, and requests exceeding available capacity must be refused. Allocation is a view of a committed parent reservation, not an additional unit; consumption changes usage within that allocation, not the reservation count.

Exhaust all orders of one prepare and one commit per sibling and one consumption attempt per sibling (attempted once even when denied), from the empty ledger, separately for conflicting and fitting cases. Prepare records the requested quantity only if it fits the then-current authoritative ledger; commit requires a prepared request and rechecks remaining capacity in the reference. The single mutation removes only that recheck, leaving prepare and all other rules unchanged. The observer recomputes `sum(reserved) <= 2` and for each sibling `consumed <= allocation == reservation`, independently of admission. Report fixture states, attempted, committed and denied transitions, violation edges, per-reason counts, explicit witness paths, and whether the 10,000-state limit truncates. Run with a 120-second timeout and 1,000,000 KiB virtual-memory bound. Also compare against the inherited capacity-one fixture's already recorded conservation semantics; this is not a claim that its single-unit guard implements a numeric allocator.

Assumptions: authoritative ledger and arithmetic, atomic serialized transitions, finite integer units, exactly two sibling requests and one consumption attempt each, no cancellation, reclamation, persistence or recovery. Concurrent *interleaving* is explored; real parallel execution, transaction isolation, authority policy, actual capacity, and enforcement are not. The fixture applies a narrow C3/T04 conservation interpretation; C1 is abstract commit only; Work Unit B/G/K are partially illustrated, and all other C1–C13/A–L obligations stay as in the inherited mapping. F1 and independent F5 review remain open.

In the reference conflict witness, both prepare while the ledger is empty, C commits two, and S is denied at commit; in the mutant, the same preparation and commits reach reservations (2,1), exceeding the independent two-unit bound. The 18 violation edges include later edges from already violating states and are not 18 independent failures. The fitting witness commits and consumes one for each sibling. Separate direct control successfully prepares, commits and consumes once then denies a second consumption. Denial consumes the one-shot fixture attempt but makes no protected ledger change; state counts include this test bookkeeping. All event permutations reachable under the fixed six one-shot attempts are exhausted; they are not all possible allocator histories.

The observer computes ledger totals and per-sibling allocation/consumption consistency independently of the admission check. This demonstrates a counterexample to checking only at prepare and a successful atomic-recheck behavior under stated assumptions; it does not establish a real implementation or atomicity. The fixture uses the inherited capacity-one conservation semantics as an external comparison, not its code as the numeric admission oracle, because that code only represents one unit and one owner. There is no implicit source or authority check. No stronger claims, F1 completion or F5 review follow. A useful next discriminator would combine recovery with a separately retained reservation ledger or currentness witness; this graph has no persistence or crash steps.
