# Accepted-content continuity after executor and holder loss — preregistration

F1's `content-continuity` fixture assumes its accepted atom survives; the separate Kernel-0 recovery experiment has real holder SIGKILL and content use, but its continuing worker survives holder loss, and the cold history kills workers only after replacement has already been established. The targeted gap here is actual termination of the original content-producing worker before the holder is restarted or a replacement worker exists, followed by fresh retrieval and use from the recovered holder. It reuses `docs/research/kernel-0/kernel0_recovery_check.py` and its actual SQLite-backed subprocess holder, without changing the existing service or equating the prototype with F1 conformance.

Pre-run hypotheses: after successful acceptance of content atom 1, SIGKILL and reap producer, SIGKILL and reap holder, start new holder on the same store, issue replacement authority, then start a distinct fresh executor. That executor's own `read` of the holder supplies actual retained bytes; no supervisor or old producer supplies the accepted value after loss. Its request to resume using a *different* valid atom must be denied without altering state; its resume using the bytes read from the holder must commit and update the expected work bit. The old authority view must show revoked after replacement. This addresses finite C5/C7 and K.20 evidence, not F1/F3 acceptance or a durability proof.

Premises: process loss only; same OS, storage and trusted supervisor remain live, normal SQLite/host behavior, successful acceptance acknowledged before kill, no crash during commit, stable fixture root/profile, control channel and holder read trusted, serialization within the prototype; finite two-atom universe. A new process opens the same committed store; replacement authority is issued by the trusted supervisor. We do not test host power loss, filesystem durability, storage tampering or rollback, isolated or untrusted holder, physical-source authentication, a real Work Unit, or arbitrary content. Both producer and holder loss are real OS SIGKILL events and separately evidenced; the oracle's pre-loss bytes serve only as external comparison, never an input to the fresh executor. Negative control is a different valid atom, not malformed input.

The producer (PID 6236) received a commit response accepting `accepted\u0000one\n`, then was killed and reaped with exit -9. The holder (PID 6229) was killed/reaped by the inherited helper, which asserts exit -9; replacement holder PID 6237 recovered the exact acknowledged state from the same store before replacement authority. The trusted management request committed replacement, showing context 0 rights 7→0 and context 1 rights 0→7. Only then was fresh executor PID 6244 created. Its only passed runtime input was the new holder channel descriptor; it read retained bytes from that holder, selected the different valid atom `accepted\u0000zero\n` as control, and sent resume using it. That was denied with no state change. Resume using the bytes it had just read committed and changed `data[0]` from 0 to 1; accepted bytes remained exact. A final holder read agreed. Parent-side comparison against the pre-loss response was an oracle, not an input to recovery or fresh executor. Fresh executor exited 0.

This finite local observation extends the prior holder-loss evidence to acknowledged content whose original executor was already dead before holder recovery and before replacement executor existed. It shows one retained bounded string (including NUL/newline) and a meaningful valid-but-wrong-content refusal. It does not establish availability after host/storage loss, physical enforcement, rollback resistance, arbitrary bytes or concurrent histories. Work Unit and F1 C5/C7 remain partial: the experiment uses a Kernel-0 prototype and explicitly trusted store, not a production Work Unit realization. F5 independent review remains outstanding. The next useful discriminator is a separately bounded failure of the storage/currentness premise: can the receiver distinguish an authentic but stale committed image after both processes die using only the restored image? Existing rollback counterexample already predicts it cannot, so any new test should compare an actual independently surviving currentness witness or a fail-closed absence case, not rerun that known stale-image example.
