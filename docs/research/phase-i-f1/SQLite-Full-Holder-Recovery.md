# Holder write at SQLite page ceiling — preregistration

The reused `kernel0_recovery_service.py` writes a small, fixed finite `View` into one SQLite row; accepted values are the short fixed strings in `kernel0_service.py`. An ordinary one-row value replacement may fit existing pages even at `max_page_count`, so the cap alone is not a meaningful full-database trigger. Prior recovery evidence covers SIGKILL cuts and lost replies, not a real SQLite resource error from a valid accepted-value update. This test retains the unmodified holder and finite policy, adding only a **disposable test-only expression index** that expands for the valid `one` value. The index changes physical write costs and is outside the inherited initialized schema, while leaving logical holder state and guard unchanged; results do not establish behavior of its original schema under natural disk exhaustion.

Two isolated temporary stores run the same setup: inherited holder establishes/grants context 0, explicitly commits accepted `zero` and sends its success reply; supervisor records that exact full view and the raw persisted view bytes before the test. Create a synthetic deterministic index on the view which is small for `zero` and grows for `one`; verify setup and index creation succeed before starting the constrained write. A disposable launcher wraps the original `Store` only to set `PRAGMA max_page_count` on its actual holder connection and log SQLite error code/name before re-raising; `Boundary`, resolver, policy, protocol and storage write execute unchanged. Both cases request the same valid `accept one` through a holder endpoint. Low-cap case sets maximum to current page count, and predicts a real `SQLITE_FULL` while writing, no successful ACK, then cold recovery of the exact previously acknowledged zero view. Neighbor control allows at most 64 pages and predicts successful accept/ACK and recovery of exact one view. Index and page limit must be in effect on the actual writer connection; distinguish a setup/index/cap failure from error during request handling and report its exact stage.

After each outcome, kill and reap only that owned holder, restart an ordinary unmodified holder on the same store, and use a separate fresh read-only SQLite subprocess to report integrity, root/profile/version and exact persisted view bytes. Compare both recovered views to the independently retained successful response appropriate to the case; check the negative client observes EOF or timeout rather than a success reply, and never infer failed commitment from missing reply alone. An explicit SQLite `SQLITE_FULL` code, raw full view/bytes/hash, client outcome, stderr/log, cold holder read, and independent integrity/bytes form the combined evidence. Raw result has both cases, PIDs, exits, page counts/cap and byte sizes. A failed prerequisite aborts or is recorded as setup failure rather than an eligible result.

Bounds: two fixed cases; 64 pages maximum positive, negative maximum initial page count; at most 1 MiB total temporary files per case verified after phases; one 8 KiB generated index key, one finite 4 KiB-or-less request; 512 MiB process virtual-address-space ceiling inherited by child holders, 60-second outer deadline and 10-second channel/process timeouts, kill/reap all owned children. No actual host disk filling, host limits, privilege or production changes. Trust SQLite/VFS/OS and process-loss behavior on a live host, disposable setup, pre-run state, instrumentation and independent reader. No host/power loss, arbitrary storage corruption, database rollback, all resource errors, error at the COMMIT instruction specifically, worker authentication, or universal no-ACK proof. The error may arise at UPDATE/index maintenance before `COMMIT`; if so describe it as write-stage failure. F1/F5 remain incomplete.

Raw JSON includes exact views, bytes, all PIDs, exit codes, logs and file sizes. The process-level 512 MiB virtual-address-space cap and 60-second outer timeout were in effect.

This is a write-stage failure, **not a failure inside the SQLite COMMIT call**. The actual holder's connection was instrumented only to configure/report its cap and log/re-raise the real SQLite exception; the source holder, policy, request and resolver were unchanged. The synthetic index was added only to temporary stores and changes physical schema and costs, so the result does not show the original initialized schema or ordinary host disk exhaustion triggers this failure. It does not prove all errors, all schedules, host power-loss durability, physical storage integrity, or an F1/F5 completion. The holder's error thread's stderr happened to be empty at kill; the separately recorded SQLite exception and client EOF are the relevant observed error evidence.
