# What does the native owner actually acknowledge?

The protected-witness fixture makes one decision record authoritative for acceptance, custody and retry. The native F3/F4 prototype has distinguishable decisions on its owner, journal and publication planes. The old successful recovery histories can be reused for a sink-only loss. They leave both protected currentness after witness loss and execution-specific replacement unresolved. This crosswalk uses pinned source and retained captures. [Prior fixture](Committing-to-a-surviving-cut.md) · [Prior authority decision packet](../astra-followup-20261125/round25/WORK-UNIT-AUTHORITY-RUST-CUSTODY.md)

## Faults and observations have distinct evidence

- **REUSE, sink loss with a live witness.** Existing native UID run-04 covers an after-append `local` event and a complete post-fsync event with an owner still `reserved`. The strict and explicit-observation recovery paths respectively publish the exact cut and settle A without a duplicate append. The old exact request can observe that accepted event after the authority path is moved. The source matches the claim: the reconciler requires an exact, unique **final** event, matching historical owner material, and a witness currently at the exact target or preceding cut. These are positive cases for that bounded recovery classifier. [Retained run and checker](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-ii-native-recovery-uid/REPORT.md) · [Reconciler guards](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-ii-native-publication-reconcile/reconcile.py#L184-L236) · [Predecessor/target check](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-ii-native-publication-reconcile/reconcile.py#L439-L457)
- **REUSE, eventless reservation and admission bound.** The final line guard classifies a reservation with no indexed event as unresolved. PR #98 refuses a new reservation while another is pending. Its A1–A6 captures distinguish ordinary fresh-ID refusal, exact historical replay and the disposition guard. Seal can complete with an unresolved reservation. This is evidence for a bounded uncertainty window, with potentially indefinite unavailability; a gate-time rerun would leave that limitation intact. [PR #98 implementation report](https://github.com/rock-solid-sites/ASES/blob/2358354c86a2b15e6ddbe81480d4c783a46e5a56/docs/research/phase-ii-native-pending-admission/IMPLEMENTATION-REPORT.md)
- **BLOCKED, protected-currentness claim across witness process loss.** The imported `witness_server` stores `current` and `revision` in a process-local dictionary and initializes them anew on server entry. The CAS changes that dictionary. The sink refuses a cold start if its full journal cut cannot be checked. This source establishes the absent persistence mechanism directly. A repeat of sink loss with the existing live witness cannot establish that mechanism. Starting a fresh witness and initializing it from a local image would change the trust premise. Source does not establish a trustworthy rule to pick the right old image for initialization. [Witness state, CAS and cold start](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-i-sol-integration/evidence/sources/receipt/research/phase-i-t18-sink-order-20261103/published-cut/cut_sink.py#L35-L100)

There is an additional boundary between the two authorities. The current F3 selector is `protected/CURRENT`, and selecting a protected record fsyncs the record and directory. The F4 witness cut contains managed authority fields and the journal hash. An effect's journal event can bind historical F3 selectors, but the current witness cut makes no general assertion of the latest F3 selector. For example, an owner-only `seal` advances F3 epoch and selected record without invoking the F4 publication wrapper. Hence two different current F3 states can agree on the F4 cut even when every source in view is genuine. A complete F4 cut can establish identity of historical F4 evidence without attesting the latest owner-side authority state. Merely putting the F4 witness on disk would preserve this limitation. [F3 selected record](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-ii-native-ownership/native_owner.py#L93-L113) · [F3 seal](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-ii-native-ownership/native_owner.py#L365-L383) · [F4 cut fields](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-i-sol-integration/evidence/sources/receipt/research/phase-i-t18-sink-order-20261103/published-cut/cut_sink.py#L101-L104)

## W5/W6 source decision

The F4 `/replace` route changes a holder label, increments the managed version and makes the position inactive. `/activate` reopens it. The sink's fresh eligibility predicate uses the version and active flags. The manager fixture constructs a current native envelope and forwards version 2 irrespective of the historical worker label. The native gate checks the selected registration, owner epoch and material at append. On the checked path, none of those values binds a mutation to an owner-authenticated Execution identity for the same continuing W/P. The protected socket and UID evidence distinguish the trusted adapter from the worker. A holder label and refreshed request arguments alone cannot distinguish a fresh request from X and an otherwise identical request from Y admitted through the same trusted adapter. If a future adapter establishes that distinction and mediates all relevant paths, it would be part of the authority boundary and would need evidence of its own. [F4 eligibility and replacement](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-i-sol-integration/evidence/sources/receipt/research/phase-i-t18-sink-order-20261103/managed-revocation/managed_sink.py#L103-L172) · [Manager forwarding and transition](https://github.com/rock-solid-sites/ASES/blob/0bd51a34700164a5eb77efe98158fa37d1a74e23/docs/research/phase-ii-native-recovery-uid/fixture/owner_controller.py#L112-L162)

**Disposition.** Reuse the existing F3/F4 evidence for the bounded histories above. W5/W6 remain unrepresented on the pinned path. A new W5/W6 execution is blocked at the absent authentic replacement interface, and a sink-only crash is a poor discriminator for witness-process loss. The next design qualification should name the first observer of each status, the exact evidence covering F3 and F4, and the fault projection. It should distinguish a surviving durable owner decision with replayable audit publication from a protected common release that a caller must see before treating both planes as current. This is source-based analysis. It does not rerun the native prototype, select an authority owner, or claim real host-loss or combined-failure conformance.
