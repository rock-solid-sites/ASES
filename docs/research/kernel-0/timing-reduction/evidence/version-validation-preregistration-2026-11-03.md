# Version-validated reads across publication — preregistration

Starting at `b144c3791`: a whole-state publication still yielded torn separate reads. Test whether a bounded validation rule distinguishes this case and whether merely incrementing a version after split publication suffices. This is a toy abstract protocol, not a Kernel-0 implementation.

Keep pre `(0,1)`, post `(1,0)`, both field and read orders. Enumerate all interleavings of chains `p0 < p1` and `begin < r0 < r1 < end`: 15 schedules per field-order pair, 60 per mode. Reader samples version at begin/end, accepts iff equal and even; rejection withholds the read and is not a successful retry. Modes: `whole` publishes both fields and increments an even version by two at p1, p0 a no-op; `late` publishes each field at its event and increments version by two at p1; `bracketed` p0 increments to odd and publishes first field, p1 publishes second and increments to even. Each combined event is an explicit atomic modeling assumption. The reference whole-state commit is p1, and independently enumerated cuts within r0..r1 determine coherence, as in the previous experiment.

Predictions: every accepted whole and bracketed read has a coherent cut, with both acceptance and rejection represented; late versioning accepts at least one incoherent tuple when a read finishes between p0 and p1. Report acceptance, rejection and coherent/incoherent accepted counts and all traces; no progress, fairness, version wraparound, crashes, multiple writers or physical implementation is claimed. Bounds 180 cases, 1,260 per-case cuts, 10 s, 1 GiB; explicit case and cut truncation controls. An accepted equal-even sample is not asserted sufficient beyond this model.
