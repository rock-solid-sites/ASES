# Native cross-job capacity handoff — bounded integration packet

ASES-4 priority D actual resource-controller integration, base 27bcc552 (#42 includes #41/#40/#39/#33/#32/#31/#29). Maintained Rust tests over actual Store, Unix gateway/session/driver and owned fixed Child. This is development integration testing, not independent review or CI work. No runtime change without an actual failing case and root design decision.

WHY: native exit/cancellation and unlaunched cancellation now have complete single-job histories. Verify their effect on admission of a DIFFERENT job sharing max_parallel=1 and finite budget; balance snapshots alone are insufficient to establish actual next-job admission. Unknown custody or merely observed exit must not release capacity, while committed proper finalization or guarded unlaunched cancellation must allow the next job.
WHAT: one native integration test target with bounded fixed workers and actual Store reservations on the shared scoped environment. Use existing lifecycle interfaces and existing synthetic local meter/account fixtures, not a second scheduler model. Scope/TTL/capacity must be chosen so a refusal is attributable to the intended held environment slot or meter, not stale catalog/profile/TTL. Preserve actual errors plus job/event/balance snapshots and worker markers at every cross-job attempt.

Histories: (1) running A refuses B reserve, actual A exit observed still refuses B, explicit finalization allows B reserve/ack/native launch once; (2) real gateway loss -> cold unknown -> worker's bounded file-release self-exit, still no trusted stored exit -> B remains refused; future expiry sweep cannot expire RUNNING or free its slot; no PID adoption or claimed finalization; (3) known missing-program preflight leaves A AUTHORIZED/held and B refused; actual new unlaunched cancellation closes A/releases, fixing trusted program then B reserve/ack/launch succeeds; (4) explicit cancellation driver A observes exact exit/finalizes cancelled, B admission and native launch succeeds with A no longer live; (5) two fresh Store connections race reservation of two different jobs under max_parallel=1, exactly one reserve succeeds, loser no job/effects/worker; cancel winner via existing unlaunched route then loser can reserve. Label actual observed ordering only. Keep each scenario isolated so lingering unknown state does not contaminate later histories.

HOW CERTAIN: hypotheses tied to existing state/slot accounting, requiring actual admission results and real-process histories. WHAT-NOT-TESTED: providers, host/power loss, hostile same-UID code, arbitrary process trees, hard wall quiescence, automatic repair of unknown liveness, or production accounting. Bounded test cleanup may release a fixed fixture worker but never promote its unobserved exit into Store evidence.

Capture raw requests/replies/errors/Store events/balances/worker markers, source and executed-binary SHA256s, exact Cargo command/stdout/return code. Version failed attempts/source snapshots before edits; do not overwrite raw evidence. Run new target once after fixture is ready; affected existing targets only if a runtime/source fix is required. Avoid duplicate broad regression. One Cargo at a time; share existing target/toolchain, offline/locked/no incremental/debug. Frequent commits/push on this isolated branch, draft PR and Work Notes checkpoint; no main merge/deploy, CI/review/backup/provider/host work.
