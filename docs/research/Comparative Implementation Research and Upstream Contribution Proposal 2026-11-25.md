## Proposed research extension, not an obligatory workflow
Start with an unresolved behavior/claim/requirement or research question, establish relevant constraints and cheapest useful evidence. Find existing mechanisms across domains, including well-maintained upstream implementations and independent test/benchmark systems. Record narrow mechanism/source/identity, actual applicable claim and limits. Study source and existing test results before adding new tests. Distinguish what is observed from conjecture; do not mistake source review for live execution. When necessary run a pinned, controlled, comparable experiment; re-run the relevant donor's own suite first, use common fixtures only if semantics comparable, document environments and assumptions, qualify the oracle with compliant/violating controls where possible. Measure overhead and correctness at the same relevant boundary; test transfer to materially different object when claiming generality. Retain useful null/negative/inconclusive results and rejected approaches, not every log. 
Three outputs can coexist: (1) transferable mechanism/lesson with conditions and evidence, (2) project-specific fit or reason not to adopt, (3) upstream discrepancy or general improvement proposal. Use separate standards of evidence: our constraints are not upstream guarantees; reproduce attributed defects against actual upstream and check latest relevant revision; no defect claims solely from mock or non-equivalent benchmark. Upstream improvement need not fix a defect; show baseline/correctness preserved/cost and applicability; respect maintainers' scope, license, responsible disclosure where applicable. Offer minimal reproduction or focused contribution via maintainers' preferred process, review before publication; acceptance not goal. Follow specialist upstream changes as compatibility evidence; no automatic import or installation, avoid permanent fork by default. Temporary fork only for useful bounded upstream change. Independent reproduction and adverse review proportionate to risk; avoid same-family self-approval of critical claims. 
## Research execution and evidence boundary
Public comparative repo with pinned upstream checkouts, machine-readable manifest, small synthetic fixtures and minimal benchmark/test drivers is one suitable mechanism, not universal home. No private ASES code/records, credentials, authenticated sessions or user data in public artifacts. Check license/terms, dependencies, trust, execution authorization and costs; isolate untrusted code, least-privilege CI, no secrets/publishing/deploy jobs. Standard public GitHub hosted runners are free, useful but not rationale to run unnecessary tests or publish private work. Use private project-native repo or disposable environments for private or specialized checks, local machine for real local resource claims. Avoid separate repos per investigation when an existing home fits; no monolithic lab runtime or compulsory fork. Keep upstream revision manifest + dependency locks where feasible, test commands/fixture inputs/seeds, controlled environment, raw/summary evidence adequate to reproduce, claim/measurement limits, output classification and next decision. Pin commits not blob SHA for checkout; stable source links; preserve durable accepted evidence and minimal reproduction not temporary branches. 
## Open formalization decisions
1. Scope: exploratory technique research AND empirical testing; should method cover broader research with non-executable evidence? Likely yes with distinct evidence boundaries, not obligatory benchmark.
2. Integration: prefer additions to existing upstream compatibility and testing/assurance proposals with one shared research process, possibly a short cross-reference/guide; decide after piloting, not a new active skill.
3. Repository topology: project-scoped public lab vs general shared workbench (one repo per coherent research theme, or existing home); decide based on coherence, access and license, not quota alone. CHATWS first practical candidate; existing property/stateful pilot comparison as second independent context; no launch yet.
4. Evidence/transfer: what is minimum portable record? Candidate fields claim/question, provenance, conditions, result/limitations, reproduction, changed decision and upstream disposition; proportionate to work, not universal bureaucratic template.
5. Contribution threshold: reproducible upstream problem or demonstrably general optimization; current version and existing issues checked, independent validation proportional, maintainers' process respected. Security concerns follow responsible disclosure, not automatic public reproducer. 
6. Promotion: compare marginal improvement in test relevance, time/cost, reuse and contribution value to existing process; pilot before adoption. WNASES-10/14 and ASES-7 are existing relevant records, not proof of approval. No compulsory new agent workflow. 
Next discussion: sharpen distinction between research objects, techniques and assurance instruments; decide minimal evidence/contribution rules, then run CHATWS public synthetic pilot and another suitable cross-project case if approved. Evaluate whether existing methods need amendment or only a derived guide. Preserve findings regardless of candidate adoption. No formal status changes yet.
