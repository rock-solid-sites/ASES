## Proposed research extension, not an obligatory workflow
Start with an unresolved behavior/claim/requirement or research question, establish relevant constraints and cheapest useful evidence. Find existing mechanisms across domains, including well-maintained upstream implementations and independent test/benchmark systems. Record narrow mechanism/source/identity, actual applicable claim and limits. Study source and existing test results before adding new tests. Distinguish what is observed from conjecture; do not mistake source review for live execution. When necessary run a pinned, controlled, comparable experiment; re-run the relevant donor's own suite first, use common fixtures only if semantics comparable, document environments and assumptions, qualify the oracle with compliant/violating controls where possible. Measure overhead and correctness at the same relevant boundary; test transfer to materially different object when claiming generality. Retain useful null/negative/inconclusive results and rejected approaches, not every log. 
Three outputs can coexist: (1) transferable mechanism/lesson with conditions and evidence, (2) project-specific fit or reason not to adopt, (3) upstream discrepancy or general improvement proposal. Use separate standards of evidence: our constraints are not upstream guarantees; reproduce attributed defects against actual upstream and check latest relevant revision; no defect claims solely from mock or non-equivalent benchmark. Upstream improvement need not fix a defect; show baseline/correctness preserved/cost and applicability; respect maintainers' scope, license, responsible disclosure where applicable. Offer minimal reproduction or focused contribution via maintainers' preferred process, review before publication; acceptance not goal. Follow specialist upstream changes as compatibility evidence; no automatic import or installation, avoid permanent fork by default. Temporary fork only for useful bounded upstream change. Independent reproduction and adverse review proportionate to risk; avoid same-family self-approval of critical claims. 
## Research execution and evidence boundary
Public comparative repo with pinned upstream checkouts, machine-readable manifest, small synthetic fixtures and minimal benchmark/test drivers is one suitable mechanism, not universal home. No private ASES code/records, credentials, authenticated sessions or user data in public artifacts. Check license/terms, dependencies, trust, execution authorization and costs; isolate untrusted code, least-privilege CI, no secrets/publishing/deploy jobs. Standard public GitHub hosted runners are free, useful but not rationale to run unnecessary tests or publish private work. Use private project-native repo or disposable environments for private or specialized checks, local machine for real local resource claims. Avoid separate repos per investigation when an existing home fits; no monolithic lab runtime or compulsory fork. Keep upstream revision manifest + dependency locks where feasible, test commands/fixture inputs/seeds, controlled environment, raw/summary evidence adequate to reproduce, claim/measurement limits, output classification and next decision. Pin commits not blob SHA for checkout; stable source links; preserve durable accepted evidence and minimal reproduction not temporary branches. 
## Open formalization decisions
1. Scope: exploratory technique research AND empirical testing; should method cover broader research with non-executable evidence? Likely yes with distinct evidence boundaries, not obligatory benchmark.
2. Integration: prefer additions to existing upstream compatibility and testing/assurance proposals with one shared research process, possibly a short cross-reference/guide; decide after piloting, not a new active skill.
3. Repository topology: project-scoped public lab vs general shared workbench (one repo per coherent research theme, or existing home); decide based on coherence, access and license, not quota alone. CHATWS first practical candidate; existing property/stateful pilot comparison as second independent context; no launch yet.
4. Evidence/transfer: what is minimum portable record? Candidate fields claim/question, provenance, conditions, result/limitations, reproduction, changed decision and upstream disposition; proportionate to work, not universal bureaucratic template.
5. Contribution threshold: reproducible upstream problem or demonstrably general optimization; current version and existing issues checked, independent validation proportional, maintainers' process respected. Security concerns follow responsible disclosure, not automatic public reproducer. 
6. Promotion: compare marginal improvement in test relevance, time/cost, reuse and contribution value to existing process; pilot before adoption. WNASES-10/14 and ASES-7 are existing relevant records, not proof of approval. No compulsory new agent workflow. 
Next discussion: sharpen distinction between research objects, techniques and assurance instruments; decide minimal evidence/contribution rules, then run CHATWS public synthetic pilot and another suitable cross-project case if approved. Evaluate whether existing methods need amendment or only a derived guide. Preserve findings regardless of candidate adoption. No formal status changes yet.


## Discussion extension — reciprocal empirical improvement (2026-11-25)

Operator clarifies that existing testing work should be integrated with comparative implementation research: subject candidate software to applicable existing test techniques and suites; contribute verified regressions upstream; use the increased diversity of subjects to improve the testing methodology itself. These are reciprocal research objectives, not two separate laboratories. Extend the existing experimental laboratory and assurance-selection research, without creating an automatically adopted canonical method.

- Apply relevant existing tests first. Separate portable behavioral properties, parameterized generators, fault-injection/replay machinery and project-specific oracle/adapters. Do not transplant a project-specific acceptance rule to an unrelated implementation or run every available test indiscriminately. Distinguish target-native suite, cross-implementation comparable property, and local-fit experiment; record exclusions.
- Two evaluation axes: (A) evidence about the subject (conformance, discrepancy, performance, fitness); (B) evidence about the instrument (sensitivity, specificity, scope, transfer/adaptation effort, cost, reproducibility, incremental detection beyond existing tests). Do not infer either from the other. Valid no-discrepancy, rejected-oracle and inconclusive outcomes.
- Use real source-pinned implementations across materially different domains, runtimes, maturity and failure modes. Candidate selection follows research relevance rather than convenience or expected bug yield. Evaluate on known-good/known-bad controls, historical defect/fix pairs when available, and controlled mutants or injected failures where meaningful. Historical regression reproduction and synthetic sensitivity must not be reported as newly discovered live defects. For methodology transfer, preserve an independent held-out subject or case where feasible; avoid tuning and scoring on the same known examples. Compare deterministic baseline and donor-native tests against the added technique under comparable effort/resource limits; do not equate number of tests or defects with progress.
- A confirmed discrepancy should become a minimal executable reproducer, with attributable expected behavior, pinned revision, environment and scope. Establish it reproduces on relevant current upstream, check existing issue/fix, follow licensing/contribution and responsible disclosure requirements, and propose a focused regression test and/or fix when useful. Public contribution is normally desirable for verified broadly useful cases, subject to review and permission; do not auto-file reports or disclose sensitive findings. Retain the portable lesson or repaired test instrument separately from project-specific acceptance tests and upstream patches.
- A reusable assurance technique earns promotion through transfer evidence: catches relevant controlled or real failures that simpler approaches miss, or reduces effort/cost without weakening confidence. Record blind spots, false alarms, oracle bugs, adapter burden and cases where the simpler test wins. Do not impose a universal suite, framework, mandatory test count or architecture. Test methodology evolves from evidence, subject to existing independent review/promotion gates.
- Initial proposed corpus: CHATWS browser donors for lifecycle, DOM resilience and response correlation; existing ASES/Paseo/OpenCode for authority/recovery; prior property/stateful pilot and HMS/Projektor/Trip'n where applicable, respecting authorized private/public boundaries and existing project-native suites. No live bookings, external model calls, private publication or executions authorized by this discussion. Public reproducible donor research repo is one suitable substrate, not a second central test system. 

Next step: inspect existing empirical lab and donor test suites, map reusable instruments and attributable properties to first CHATWS subjects, define baseline and discrimination controls before running; use findings both to assess candidates and evaluate the testing technique. Keep proposal status experimental; reconcile WNASES-10/14 and ASES-7 before promotion.

## Discussion extension — eventual public testing toolkit (2026-11-25)

Operator clarifies the intended outcome is a broadly useful tool resulting from the research and generalizations, potentially released as a separate public repository after sufficient development. The deliverable is not merely a research notebook, collection of project-specific tests, or universal mandatory framework. Distinguish the experimental corpus and runners, transferable testing mechanisms, and research/methodology findings. Preserve the existing empirical lab and its review/promotion path. At the pinned lab revision 5a1ba2cff4439bdaafa0ed2c29ff6a4caef04a02 the testing/ directory contains methods, experiments, lessons and counterexamples but no general tools/ implementation; existing scheduler-clock pilot in research/testing-assurance-pilot/scheduler-clock contains specific classifier/readback code and tests. These are inputs, not evidence of a mature reusable package.

Proposed development direction: start from existing libraries/suites and actual research needs, extract recurring mechanisms only after evidence of transfer; prefer interoperable components/adapters over imposing an all-in-one runtime. Candidate areas (not a preselected architecture): property/stateful test generation, reproducible histories and shrinking, fault injection, controlled baseline/negative cases, oracle qualification, cross-implementation comparison, replay/evidence capture and test-method applicability. Domain specifications and acceptance oracles remain with subject owners; no generic tool may invent expected behavior. Test and compare existing instruments too, avoid reimplementing proven general-purpose libraries absent a demonstrated need. AI assistance optional; deterministic tests should be independently runnable without model access where possible.

Proposed maturity gates before separate public release: demonstrate useful behavior on materially different real subjects, independently check test discrimination/replay, measure marginal benefit and adoption friction against simpler/native tools, provide a narrow stable interface and minimal docs/examples, preserve provenance/license and exclude private fixtures/credentials/project policy. Early public comparative research repositories remain legitimate before toolkit release; do not confuse a published experiment with a supported product. Select package shape, language, project home/name and release timing from evidence and user decision; no package or release chosen. Preserve negative findings and contributions upstream even when extraction is unnecessary. Existing project-native tests stay with their owners. No new implementation, repository creation, publication or launch authorized by this discussion.

## Discussion clarification — research technique versus public product (2026-11-25)

Operator distinguishes the pinned-upstream comparative repository technique (primarily reuse of Git/GitHub checkout, Actions, logs and reproducibility facilities) from the reusable testing suite/toolkit, an actual software product intended to be released free of charge. Do not turn the comparative research environment into a product, custom execution platform or mandatory standalone infrastructure. It may be a small set of existing tools, repository conventions, manifests and experiment scripts; use existing project-native CI where suitable. Public experimental repositories can support reproducibility, upstream contribution and free standard-runner access without being themselves the product.

The toolkit is a separate potential free/open-source product, intended to be independently useful outside ASES and its research subjects. Develop it from demonstrated transferable testing capabilities, retaining existing library integrations rather than replacing them without evidence. Separate experimental results and subject-specific test suites from reusable product code. Product requirements, interface, audience, distribution, maintenance and license remain to be developed from evidence; do not infer a hosted service, commercial tier, specific package format, or universal testing framework. Eventual separate public repository/release is a proposed product boundary, not authorization to publish or create it now. Research technique remains useful even if a particular toolkit component is rejected; toolkit should be usable without requiring the ASES research environment or GitHub specifically. No changes to canonical methodology or execution authorization.

## Discussion extension — composition as a formal-computation testbed (2026-11-26)

Operator identifies the final composition of independently investigated donor mechanisms as a direct experimental subject for EDASES Formal Computation, Reuse and Avoidance (Projektor ASES-25). This is a reciprocal relationship: comparative research supplies real heterogeneous mechanisms, interfaces, contracts, evidence and counterexamples; formal research supplies candidate ways to reason about composition and the necessity of adaptation, computation and verification. Neither program is subsumed into the other; the research environment remains distinct from the prospective testing product.

- Derive system-level requirements independently of donors. Characterize each selected mechanism's assumptions, guarantees, effects, identity/version, and evidence boundaries. Check compatibility and shared constraints, not merely types or successful native suites. Treat composition as its own research object with independently specified integration properties and negative controls.
- Candidate formal approaches: typed DSLs/IR and typestate to constrain legal compositions and distinguish candidate from admitted operations; recursion schemes for genuinely well-founded decomposition and combination (not arbitrary dependency graphs); lawful lenses/bidirectional transformations for suitable pure adapter/view mappings; state machines and compositional assume/guarantee reasoning for interacting lifecycle/effect boundaries. Formalize only where it improves the actual reasoning or verification; runtime authority, external effects, failure, concurrency and evidence custody remain explicit.
- Reuse/avoidance: investigate whether identity, dependency frontiers and explicit assumptions justify carrying forward a donor's evidence or results, eliminating redundant conversions/checks, or retesting only affected obligations after a change. Compare validity-check cost with rerunning; unchanged code or a passing component suite alone is insufficient to establish unchanged composite behavior. Preserve minimal reproducible counterexamples and necessary durable intermediates.
- Concrete initial baseline: [T03 composed task-slot/dispatcher](https://github.com/rock-solid-sites/extensions-comparative/blob/main/results/2026-11-26-t03-composed-slot.md), native tests 16/16 and 12/12, composed 4/4 including duplicate-effect oracle control. It exercises actual task-slot and dispatcher boundaries with synthetic effect/transport/storage, including lost replies and reconstruction; it does not establish full CLI persistence, actual HTTP authorization/validation, real browser/provider effects, or exactly-once semantics. Use the existing experiment record rather than rerun it just to demonstrate a formal technique. Existing WNCHATWS-4 owns subsequent HTTP/persisted-job composition work; no change to that scope or test authorization.
- Evaluate candidate formal techniques against ordinary composition and native/integration testing: does the technique expose an otherwise missed incompatible assumption or counterexample, establish a stronger scoped guarantee, simplify a proof or adapter, or justify measurably less computation/retesting at equivalent confidence? Include cases in which no added abstraction is warranted. A second materially different composition is needed before asserting broad transfer.

This is an experimental cross-reference, not a new mandatory stage, universal DSL, formal-method requirement, toolkit architecture, execution task, or adoption decision. Maintain existing upstream compatibility and assurance promotion gates.
