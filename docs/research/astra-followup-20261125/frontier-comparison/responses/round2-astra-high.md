**My candidate for Kernel-0 is a durable set of protected values and a separately protected set of current grants, with two kinds of authoritative change.** One replaces a value under a current grant. The other replaces or withdraws a grant under explicit configuration authority. Both decide against current state at the instant the change takes effect. Work Unit, Attachment Point, and Execution can all be expressed with those rules.

The minimality claim concerns **distinctions**, not the number of objects or opcodes. A kernel must distinguish continuing work from its current executor, current authority from evidence of past authority, and changing a work product from changing who may act. I can justify those distinctions by counterexample. I cannot justify a unique representation, a general transaction language, a delegation calculus, or a kernel object for each architectural noun. The pinned packet is the sole design source for this derivation. [Kernel-0 Evidence Packet](https://github.com/rock-solid-sites/ASES/blob/a02df749b4b3da88d3f88c1712623cec6ad5d963/docs/research/kernel-0/Kernel-0-Evidence-Packet.md)

## 1. Derivation from failure cases

Start with a durable value and an operation that replaces it. Four experiments expose what is missing.

1. **Remove the executor.** If removing it also removes the only authoritative address for the work, its successor cannot continue the same work. Some stable designation and enough state to resume must survive. This proves a continuity requirement. It does not prove that the kernel needs a work tree, an execution history, or even a separate record for each work item.
2. **Deliver an old request after replacement.** Suppose both old and new executors can write by proving “I occupy position A.” An old, delayed request carries precisely the evidence that worked yesterday. The boundary needs both a distinction between the two tenures and a way to test which tenure is current. Killing a process cannot settle the status of an already queued request.
3. **Let a writer change the rule that admits writers.** A writer with access to its own grant record can expand its scope. Moving that record into a work manifest has the same failure if a privileged interpreter obeys the manifest. There must be a protected distinction between ordinary content and facts that confer authority, wherever those facts are represented.
4. **Revoke between check and use.** An executor passes a grant check, replacement completes, then the old write becomes authoritative. Every individual check may have returned the right answer. The composition still violates supersession. Admission and mutation need a common decision point with respect to conflicting changes. Independent operations need no corresponding global order.

These experiments yield a small ontology: a **stable target**, its **authoritative contents**, a **currently valid and scoped basis for acting**, and a **decision that changes authoritative state or rejects the request**. A position is a stable target whose changing contents describe authority. An execution identity need only distinguish a tenure at that position. No persistent identity for the human, model, provider, or operating-system process follows.

## 2. A closed transition system

Here is one sufficient realization at the level of semantics. It is deliberately narrow enough that its authority can be inspected.

| State | Meaning |
|---|---|
| Data entry `d` | A stable address, an inert value, and, for conditional updates, a revision. An inert value can contain code, names, signatures, or proposed actions. Storing it invokes none of them. |
| Grant entry `p` | A stable address, a generation, and either vacancy or one execution verifier with a finite set of exact `(data address, read or replace)` rights. |
| Initial configuration | The recognized addresses, the credential authorized to configure grants in this domain, and any data addresses that permit at most one current writer. The configuration authority is an explicit initial endowment. |

There are two mutating operations and one observation rule.

- **`Bind(p, expected generation, new binding or vacant)`** requires an authenticated configuration request covering all its arguments. The expected generation must match. The proposed rights must name recognized data entries and operations. The resulting bindings must satisfy declared exclusivity. Acceptance advances the generation and replaces the entire binding. An occupied binding uses execution evidence specific to its tenure. Learning the new public generation cannot give an old executor that evidence.
- **`Replace(p, generation, d, expected revision, value)`** requires a request authenticated by the verifier currently at `p`, covering the operation and all its arguments. The generation must match, the current grant must allow replacement of `d`, and the expected revision must match. Acceptance replaces exactly one value and advances its revision. It cannot interpret the value, follow a pointer, alter a grant, or call an external service.
- **`Read(p, generation, d)`** checks current tenure and read permission before returning the value and revision. Controlling this observation matters when isolation includes disclosure. A read authorized before withdrawal can leave the reader with a copy.

Each mutating rule checks its conditions and publishes its specified result as one decision. Rejection publishes no authoritative mutation. Two `Bind` requests that would give different positions exclusive write access to the same address conflict even though they name different positions. A realization that checks only the position being edited is incorrect.

There is no caller-supplied predicate, policy program, arbitrary write set, or privileged callback. Configuration authority has substantial **effective** power: whoever can bind a controlled executor to every address can obtain every data right in the domain. Calling that principal an administrator would add no protection. Its actual power, initial provisioning, and credential custody belong in the trust statement.

I include revisions because they give a precise and inexpensive answer to conflicting edits. **They are stronger than the packet’s unconditional lower bound.** A serialized blind replacement is defensible where last-writer-wins is the intended meaning. The same qualification applies to read grants if “isolated” governs mutation alone. [Authority, configuration, and separation requirements](https://github.com/rock-solid-sites/ASES/blob/a02df749b4b3da88d3f88c1712623cec6ad5d963/docs/research/kernel-0/Kernel-0-Evidence-Packet.md#established-requirements)

## 3. Composition into the Work Unit architecture

Take a Work Unit `W` with stable addresses for its brief, draft, and review, and two grant positions `A` and `B`. The association with `W` can be established by configuration. A manifest may describe it for discovery. Editing that manifest cannot grant access to another address.

Bind an executor at `A` to read the brief and replace the draft. Bind another at `B` to read the brief and draft and replace the review. The work and the two positions survive when both bindings are vacant. A successor at `A` receives fresh tenure evidence and reads the existing work through its grant. A checkpoint needed for continuation must already have reached authoritative storage. Private reasoning lost with an executor cannot be recovered by this construction.

This gives single execution by occupying `A`, sequential execution by rebinding `A`, and concurrent execution by also occupying `B`. Disjoint data rights give isolation. Overlapping rights give sharing. The example is hybrid. A second writer can be admitted to the draft if the configured sharing rule permits it. Builder and Reviewer are descriptions of these configurations. No transition tests either name.

Three races show exactly what the construction buys:

| Competing events | Permitted outcome |
|---|---|
| An old executor submits a draft as `A` is rebound | If the write takes effect first, the successor inherits it. If rebinding takes effect first, the write fails. A successful reply to the earlier write may arrive after replacement. |
| Two authorized writers edit draft revision 8 | At most one replacement conditioned on revision 8 succeeds. The other receives a conflict. Choosing a merge, discarding an edit, or asking for review remains outside the kernel. |
| Two configurators try to assign an exclusive draft to different positions | At most one grant becomes current. Moving the right between positions can pass through vacancy. A requirement for uninterrupted, atomic handoff **between** positions would require a different encoding or a wider transition. |

There is a consequential limit to single-entry updates. If `B` reviews draft revision 8 and the draft advances to 9, `B` can still publish a review *of revision 8*. Recording the reviewed revision makes that statement unambiguous. If the desired invariant is “the current approval always applies to the current draft,” separately updating draft and approval does not enforce it. Co-locating the distinguished state in one protected entry works **if its writers may replace the whole entry**. If authors and reviewers must control different fields, that shortcut destroys separation of authority. A fixed review transition or a narrowly scoped multi-entry condition would then be justified. The packet does not establish that invariant. [Work Unit adequacy constraint](https://github.com/rock-solid-sites/ASES/blob/a02df749b4b3da88d3f88c1712623cec6ad5d963/docs/research/kernel-0/Kernel-0-Evidence-Packet.md#work-unit-as-an-adequacy-constraint)

## 4. Elimination tests

| Candidate element | Attempted reduction and verdict |
|---|---|
| Stable data address | A stable path, a tuple, or a field inside a larger durable value can supply it. Removing every continuing designation makes “resume this same work” depend on a lost executor or an unacknowledged external authority. **Stable reference is necessary somewhere.** |
| Separate position address | With one executor, the current binding can be a field on the work. With two independently replaceable positions, one undifferentiated binding either invalidates both or lets the replaced one continue. **Independent positions require distinguishable bindings.** A table per Work Unit is optional. |
| Generation and execution verifier | A fresh unforgeable tenure credential checked against current state can serve both purposes. A public counter alone permits an old executor to quote the new count. A permanent shared credential alone admits delayed requests after replacement. **Freshly distinguishable authority is necessary.** Two separate fields are optional. |
| Explicit rights set | Static wiring or distinct protected endpoints can encode the same restriction. A single undifferentiated “active executor” check lets the review writer overwrite the draft. **Scope is necessary wherever permissions differ.** A rights list, role model, and general delegation system are optional. |
| Protected `Bind` | It can share machinery with conditional replacement if the target type fixes who may modify it and what states it may hold. Giving ordinary data writers that same unrestricted operation enables self-grant. **A distinct authority-changing rule is necessary.** A separate opcode is optional. Withdrawal is binding to vacancy. |
| Revision on data | Expected-value comparison suffices when intervening history is irrelevant. It misses `X → Y → X` when a decision must be invalidated by *any* intervening change. Blind writes suffice for deliberately overwriteable values. **The conflict contract determines the minimum.** |
| Exclusive-writer declaration | One designated writer position plus exclusive occupancy can enforce it statically. If multiple positions may independently acquire the same exclusive resource, checking vacancy at each position fails. **The invariant needs a common point of enforcement.** A lock manager is optional. |
| Durable history, scheduler, clock, process registry | Current durable state suffices for the traces above. Replacement can be explicit, pending work can be rediscovered, and vacancy consumes no execution machinery. Audit replay, timed expiry, automatic failover, and fairness would each need additional premises. **None is established as intrinsic.** |

A single universal `commit(if predicate, apply patch)` would shorten the vocabulary while moving almost the entire design into the predicate, patch validator, and authority for installing them. Conversely, declaring three object types named after the Work Unit diagram would leave the revocation race entirely unanswered. Neither move improves the minimality argument.

## 5. Indirect authority, revocation, and recovery

**Direct rights compose only over independent direct actions.** An executor with read access to a private draft and replace access to a shared report can copy the draft into the report. Both actions pass the rules. Preventing that flow would require a stronger isolation contract. Similarly, if an executor can write a queue and a more privileged service automatically obeys the queue, queue access confers indirect command authority. Treating the queue as inert inside Kernel-0 settles only the kernel semantics.

A privileged consumer has two defensible interpretations. It can make a fresh decision under its own grant and take responsibility for the result. Or it can act on behalf of the originating execution, in which case the authoritative action must still check the origin’s current tenure and scope. A message saying “previously authorized” cannot supply that check. If autonomous delegation is required, copying a parent’s rights into a durable child grant fails cascading revocation. The child must retain an enforceable dependency on live parent authority, or withdrawal must invalidate dependent grants before they can act again. The direct-grant candidate avoids that extra state by giving executions no grant-creation right. The packet leaves this choice open.

**Revocation is prospective at a specified boundary.** It can prevent a later authoritative write, including one formulated before revocation. It cannot erase a disclosed value, undo an accepted write, or recall an instruction already accepted by an independent recipient. A grant protects whatever operations actually pass through it. If two kernel addresses reach the same writable external object through an unchecked alias, apparent isolation of the addresses proves nothing about that object.

**Recovery must preserve withdrawals as carefully as work.** Restoring yesterday’s draft together with yesterday’s still-valid binding can resurrect a superseded executor. A sufficient recovery contract returns a consistent authoritative state containing all acknowledged decisions and admits no competing recovered authority. A system unable to establish that contract must withhold new authoritative access until it can fence the old authority and establish the surviving state. An execution crash, a lost acknowledgement, and rollback of the authoritative store are three different faults. After a lost acknowledgement, retrying the same conditional write cannot apply it twice, but a later revision alone may not establish *who* performed the original write. Durable receipts are warranted if callers require that stronger answer.

**An unresolved external effect has a hard information limit.** Consider two runs with the same durable local intent. In one, a recipient performed the action and its reply was lost. In the other, the request never arrived. After a crash, local state is identical. Retrying may duplicate the action in the first run. Suppressing retry may omit it in the second. Kernel-0 cannot guarantee both completion and absence of duplication from that evidence. Recording `unresolved` is truthful. A recipient that durably deduplicates by operation ID, or offers authoritative status tied to that ID, changes what can be concluded. A local outbox alone does not. If a recipient’s response affects authoritative behavior, the model must represent receipt, attribution, and correlation as inputs. A timeout by itself establishes no recipient outcome. [External effects and assumptions](https://github.com/rock-solid-sites/ASES/blob/a02df749b4b3da88d3f88c1712623cec6ad5d963/docs/research/kernel-0/Kernel-0-Evidence-Packet.md#external-effects-and-assumptions)

## 6. Assurance boundary and remaining decisions

The candidate assumes that tenure evidence cannot be forged or recovered by a superseded executor, request evidence binds the exact arguments, protected targets have unambiguous identities, every claimed authoritative access is mediated, and accepted conflicting decisions survive recovery in a consistent order. These are concrete realization obligations. In particular, implementing the check in one service and the write in another is insufficient without evidence that replacement cannot intervene. The bootstrap configuration credential is a trust root in this candidate. Revoking or recovering that root requires an expressly identified authority above it or a separate recovery protocol.

An adequate model would represent submission, authoritative decision, reply delivery, replacement, crash, recovery, and any claimed recipient action as distinguishable events. It should test delayed old requests, concurrent attempts at exclusive grants, stale configuration requests, lost replies, and rollback. Modeling an external call as a single invariably successful step would erase the two runs that establish the recovery limit. Proof over this model would still leave correspondence with credentials, storage, adapters, and recovery procedures to be established. [Verification requirements](https://github.com/rock-solid-sites/ASES/blob/a02df749b4b3da88d3f88c1712623cec6ad5d963/docs/research/kernel-0/Kernel-0-Evidence-Packet.md#verification-requirements)

I find **no contradiction among the established requirements**. Several stronger readings cannot be satisfied together: immediate revocation and continued disconnected acceptance under cached authority, retroactive secrecy and prior disclosure, or guaranteed exactly-once external completion with an uncooperative recipient and ambiguous delivery. The candidate chooses current-state admission, prospective withdrawal, and explicit uncertainty. It also assumes a provisioned domain of addresses. Untrusted creation of arbitrary new Work Units, resource reclamation, and dynamic cross-domain sharing would reopen allocation and configuration authority.

The remaining research questions with the greatest effect on kernel size are:

1. **What counts as an authoritative resource?** If it is a kernel value, direct mediation suffices. If it includes a filesystem, provider session, credential, or external actuator, the design must identify every path of use and where withdrawal becomes effective.
2. **What does isolation promise?** Independent mutation, confidentiality at read time, and prevention of downstream information flow require substantially different mechanisms.
3. **Which invariants span independently authorized entries?** A concrete example that cannot tolerate vacancy, stale attribution, or single-entry publication would justify expanding the transition vocabulary. Without one, general transactions are premature.
4. **Who may create, subdivide, transfer, and recover authority?** Provisioned direct grants satisfy the architecture demonstrated here. Executor-created descendants, independently revocable subgrants, and recovery of configuration authority each demand additional semantics.
5. **What must a successor be able to know?** Continuing from the last authoritative state, identifying the outcome of a particular lost request, and proving what happened outside the kernel are different recovery contracts.

On the narrow reading supported by the packet, **protected conditional replacement plus independently revocable, scoped tenure is the smallest candidate I can defend**. The strongest reason to enlarge it would be a specific invariant involving two authority holders or an external recipient, together with a pair of executions this candidate cannot distinguish but ASES is required to treat differently.
