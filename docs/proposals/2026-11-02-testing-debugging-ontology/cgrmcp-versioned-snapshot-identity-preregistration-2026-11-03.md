## Preregistration addendum: endpoint namespace collision discovered before ID tests

Date 2026-11-03. Even when 1.6.0 and 1.6.2 stores are separate, their public snapshot ID uses only repository name, commit SHA prefix and truncated URL hash, not the index producer. The same Git commit can therefore produce **the same public ID in two different engine-version scopes**. If a long-lived client accidentally switches endpoints, a request with the old ID could silently resolve to a new 1.6.2 graph instead of being rejected. The earlier recommendation to retain two endpoints solves continuity only if endpoint affinity remains correct; an explicit versioned ID is a stronger defense.

**New hypotheses:** (I1) for the same source commit, an opt-in version-scoped store can mint a different, protocol-valid ID (e.g. a digest of the producer version inserted before the frozen SHA/hash suffix) while leaving unscoped legacy ID generation unchanged; (I2) a new endpoint refuses an old ID, and the old endpoint retains its original ID; (I3) cache fast-path cannot silently accept an unnamespaced ready manifest imported into a versioned store, even if its version field claims 1.6.2; (I4) original unscoped source provenance and 1.6.0 compatibility tests remain unchanged.

**Falsifiers:** same ID in old and new scopes, new routing of the old ID to the new index, mismatch misclassified as valid, ambiguous legacy routing, or a new ID rejected by `isValidSnapshotId`. The namespace marker must be deterministic and bounded within the existing 80-character prefix and retain the 12-hex SHA / 6-hex URL suffix structure. Do not change existing legacy IDs or reassign old `by-id` entries. No production cutover or data deletion authorized.
