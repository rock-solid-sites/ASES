## Remaining discriminating tests

1. Produce matched **optimized builds**, warm compilation measurements and multiple benchmark repetitions with confidence ranges. Account for toolchain/dependency setup separately.
2. Test input validation and overflows at the wire boundary, incl. malformed JSON, unrecognized fields, missing fields, integers outside signed 64-bit range and negative values. Note: Haskell uses unbounded `Integer`, Rust uses `i64`; equal wire semantics need explicit specification.
3. Test **atomic concurrent reservations, billing transitions, stale observations, delayed reports, reconciliation and crash recovery** under identical workloads.
4. Compare explicit state-machine analytical models to constraint/accounting/event approaches for *defect-finding effectiveness*; no commitment to an all-state-machine architecture or kernel-0.
5. Evaluate property-based testing and formal verification effort; then consider Pumpkin solver integration, incremental computation reuse, Tidepool-style composition and costs of Rust compilation optimizers such as Blaze.

### Isolation experiment

Added `--bench-core PASSES` to both binaries. Both parse identical input **once**, then loop over the exact same existing admission function with a deterministic changing `usage` offset. A separate Python oracle verifies all aggregate counts and reason/checksum values on each run. The loop *does not construct or serialize one JSON object per decision*, and core time is recorded with the runtime's native monotonic clock after parsing, before summary JSON serialization.

Workload: 1,025 distinct cases × 240 passes = **246,000 decisions**; 2 warmups, 7 measured repetitions per build. Expected checksum: `accepted_count=13497`, `charge_sum=1296197`, `reason_sum=1341137`, `evaluations=246000`. Both languages passed checksum validation.

| Median (7 samples) | Rust dev | Haskell -O0 | Rust release | Haskell -O2 |
|---|---:|---:|---:|---:|
| Native timed decision loop | 24.2298 ms | 517.0812 ms | 2.5328 ms | 31.6143 ms |
| Whole process for same loop request (including one parse) | 32.0546 ms | 546.8685 ms | 4.3018 ms | 52.9923 ms |
| Native timed p95 | 28.6947 ms | 523.4293 ms | 2.5846 ms | 32.7104 ms |

The optimized Rust loop was **about 12.48× faster than the optimized Haskell loop** on this micro-workload. The distinction remains after excluding per-case JSON encoding, so JSON processing does **not** fully explain earlier differences. However the implementations use different representations (Rust `i64` and a lightweight borrowed verdict vs Haskell `Integer`, `Text`, and a strict verdict); compiler optimization, allocation, inlining, and the small synthetic workload remain confounders. This experiment does **not** measure ecosystem value, verification quality, modeling simplicity or composed execution.

**Separate whole-program comparison:** For the older 12,300-case, ~3.38 MB JSON request (9 repetitions), medians were Rust dev `131.181 ms`, Haskell -O0 `427.287 ms`, Rust release `20.741 ms`, Haskell -O2 `257.991 ms`. Those times include process launch, parsing, deciding, and output serialization. Different input sizes and pass patterns mean the two benchmarks cannot be naively subtracted as though they were the same experiment.

Exact GNU `time -v` wall-clock values and peak RSS are retained in the archived job artifacts; cargo summaries and GHC log timestamps provide approximate live figures.

|---|---:|---:|---:|---:|

Changed-source Rust values come from cargo summaries; Haskell edited values are approximately reconstructed from timestamped CI logs because exact elapsed fields in artifact `.time` files were **not printed in the trace**. Do not treat them as high-precision measurements.

The cold comparison **is not controlled for dependency compilation**: Haskell Aeson was installed as precompiled Debian packages; Rust Serde dependencies were downloaded and compiled. The edited test is a **single-file expression change**, not a multi-module edit or Rust/Haskell dependency-graph stress test. No Blaze integration or Haskell large-project compilation claims are supported.

### Selection implications

1. **Rust currently leads runtime performance and small source-edited rebuild time** for the actual conventional admission implementations tested.
2. **Haskell remains a first-class candidate** until solver integration, complex typed constraints, formal verification effort and composition/recomputation are evaluated. A single 246k-decision loop cannot decide system architecture.
3. New low-level benchmarks must retain the shared oracle, relevant compiler and library identities, common runner, raw sample traces and an explicit *which work is included* label.
4. Future discriminators: multi-module compile graphs, solver integration (including Pumpkin), arithmetic representation equivalence, property-based and proof obligations, incremental recomputation/Tidepool composition, and contention-aware real scheduling.

GitHub Actions has corresponding source-workflow configuration, but **GitHub execution status remains unverified**. GitLab evidence is the verified execution record.
