# P6 — Typed records separate failed CI, intended RED, oracle error and acceptance

**Result: QUALIFIED_WITHIN_SELECTED_CONTROLS; wider adoption DEFERRED.** Using original P5 red/green CI archives rather than only their summaries, a dependency-free Python envelope validator admitted three legitimate records and rejected 16 deliberately invalid mutations for their intended reasons. The source archive's P5 **CI failure** remained an immutable observation; subsequent evidence of a **test-fixture error** was a separate attributed interpretation, not a silently rewritten application defect.

## Actual discriminating outcomes

| Test object | Expected outcome | Observed |
| --- | --- | --- |
| Original P5 red run, with failed CI and assertions | A valid *record of failure*, not a product-failure proof | Accepted |
| P5 corrected green run, with intended mutant assertion failures | Overall qualified suite PASS while individual negative controls are RED | Accepted |
| Green evidence with archive status `NOT_VERIFIED` | Express uncertainty without fabricating a hash claim | Accepted |
| Fabricated/invalid evidence envelopes | Reject each specific misconception without rejecting the three legitimate neighbors | **16/16 rejected** |

Invalid probes included a single overloaded top-level status, an impossible job outcome, duplicate event IDs, mismatched run linkage, missing evidence references, a PASS assertion with nonzero failures, a target-defect claim based only on an unqualified oracle, nonexistent causal evidence IDs, a claimed completed review without provenance, unapproved acceptance, an archive declared complete without a digest, and unsupported source/decision/enum combinations. The driver checked **why** each probe was rejected, not merely that validation returned an error.

## Correction discovered during P6 itself

First P6 execution: [GitLab pipeline 3016045716](https://gitlab.com/rock-solid-sites-group/rock-solid-sites-project/-/pipelines/3016045716), job `17652145327`, **FAILED**. Its initial aggregation mistakenly asserted that a successful P5 suite could contain *no failed checks*. But P5's valid experimental design intentionally included faulty Rust and Haskell variants whose failed checks proved defect detection.

This was **P6 instrumentation/aggregation error**, not an application defect. The corrected `evidence_semantics_p6.py` distinguishes failures in the correct candidate (unexpected in a successful run) from failed checks in deliberately faulty candidates (expected and valuable). The original failed job's artifact is retained, including its absence of a completed P6 report. The preregistered plan was not rewritten.

**Caution:** The raw individual assertion results and the overall suite result are different semantic levels. A run may pass by correctly catching deliberately injected faults. Any model that turns every failed check into an overall suite failure loses precisely the information the methodology is intended to preserve.

## What is supported — and what is not

**Supported within the selected controls:** execution versus assertions versus instrument quality versus claim interpretation versus archive integrity versus authorized decision can be represented as separately typed events; selected structurally invalid and conceptually conflated records can be rejected; source red/green history can be preserved without substituting a later finding for the original output; complete source artifact integrity can be checked independently; expected RED controls need not be confused with unexpected failures.

**Not supported:** semantic truth of any arbitrary claim, true identity of an actor named in a record, authorization merely because a string says so, genuine route and clean-room independence merely because a provenance field is populated, universal JSON Schema conformance, arbitrary CI provider compatibility, real distributed accounting or practical human-review reconstruction.

**Evidence-model limitations:** the prototype has no authenticated authoritative actor registry, canonical claim registry, verified event clock/ordering or universal event reference resolver. The proposed categories remain experimental. A source-code test fixture's inputs can require reconstruction from pinned source even if the archived machine results contain expected/observed triples.

**Next discriminators:** independently review the P5 evidence from archived bytes, run a *blinded* conformance/fault-finding comparison separate from known planted faults, and test the experimental event categories against a second system (for example, Trip'n monitoring) before making them canonical.

**Decision:** the testing-and-assurance and ontology proposals remain drafts. No production Resource Solver, CI monitor or Orchestrator policy was changed.
