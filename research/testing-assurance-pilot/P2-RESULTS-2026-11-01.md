# P2 — Trip'n production-invariant monitor: evidence and method evaluation

**Decision: DEFER methodology promotion and production-monitor changes.** P2 executed the pre-registered safe synthetic checks on an isolated private GitHub research branch, not on the live site. It found a real **test-sensitivity gap** in the existing detector and a separate **observation/cadence gap** in CI history. These are assurance findings, not proof of a booking problem, present production outage, or unauthorized requirement to fail closed.

## Prospective synthetic execution and discrimination

- [GitHub Actions run 41348887554](https://github.com/TripN-Chill-Zone/tripn-astro/actions/runs/41348887554), [job 124974548387](https://github.com/TripN-Chill-Zone/tripn-astro/actions/runs/41348887554/job/124974548387): **SUCCESS**, source revision `32a2968d6bee97532b3fdc78f6609b6f72f87ca4`, Node `v24.19.0` Linux x64.
- The only mutation was replacing the exact `const forbidden = FORBIDDEN_BODY_MARKERS.find(...)` in a temporary copy with `const forbidden = undefined` to bypass the explicit forbidden-content check.
- The original existing six self-test fixtures passed **6/6 on the correct module and 6/6 on the broken mutant**. In particular, the old LiteSpeed stopped-page fixture fails other guards (bad server / missing required content), so it does **not** test sensitivity of the forbidden-marker guard in isolation.
- A new **compliant neighbor** used a HTTP 200, Cloudflare-like server and `cf-ray` header with `Hostels in Tirana` text; both versions correctly accepted it.
- A new **violating neighbor** used the same valid headers/required text but added `website has been stopped`. The correct implementation returned `ok=false`, detail `forbidden body marker: website has been stopped`; the mutant incorrectly returned `ok=true`. **New control detects a real legacy-test blind spot**. This is stronger evidence for controlled counterexample selection than the four deliberately targetable mutations in P1.
- Separate DNS boundary observation: `checkDnsAnswers(['203.0.113.7'], ['104.21.0.0/16'])` rejects, but the same address with `null` Cloudflare range list is accepted. The present implementation therefore **cannot verify Cloudflare membership when its ranges are unavailable**. Whether such uncertainty must block or merely degrade the check is an UNRESOLVED requirement decision; do not label it a definite implementation violation without authority.

The synthetic controls and instrumentation passed in **83.701 ms**; CI job start `20:50:18Z`, completion `20:50:41Z` (~23 seconds including checkout, Node installation and artifact upload). Seven machine-reported P2 assertions were true, while the legacy test's green result on the mutant was itself the observed sensitivity failure. These observations do not establish a general mutation-score threshold.

## Retrospective real workflow audit (separate from synthetic CI)

- Existing monitor: `Production Invariant Check`, configured at `7,37 * * * *` (nominal twice hourly). It includes six self-tests and six live DNS/HTTPS/content checks. Failures may open or comment on GitHub issues; no additional dispatch was made for P2.
- 196 historical workflow runs were enumerated and persisted as of 2026-11-01T20:47:31Z, spanning 2026-09-24 to November 1. **189 SUCCESS, 7 FAILURE**; 194 `schedule` and 2 `workflow_dispatch` events.
- Among the seven failures, **five** were `tripn-astro.pages.dev` DoH `Status=2` errors affecting the Pages comparison and Pages HTTPS probes while both apex and www HTTP checks passed. **One** was a 30-second isolated apex HTTPS timeout, while www and the pages.dev comparison passed; **one** was the deliberately simulated failure used to validate the alert path on September 24.
- These are **monitoring observations**, not a measured uptime percentage. A passing apex observation does not prove every client was unaffected; a failing comparison hostname is not necessarily an outage of `tripnhostel.com`. No sustained customer-facing outage was demonstrated by the seven inspected logs.
- Latest successful production-monitor run examined: [41325554309](https://github.com/TripN-Chill-Zone/tripn-astro/actions/runs/41325554309), 2026-11-01T16:17:22Z, 6/6 self-tests and 6/6 live checks. The run listed **zero** GitHub Actions artifacts, and its native log is subject to GitHub retention.

### Schedule guarantee is not demonstrated

Of 194 observed scheduled executions between `2026-09-24T19:29:04Z` and `2026-11-01T20:47:31Z` (913.3075 hours), the **median actual scheduled-run interval was 4.8394 hours**, p95 **7.1239 hours**, maximum **9.8803 hours**, minimum **2.1144 hours**. The theoretical 30-minute schedule corresponds to approximately **1,827 expected slots** across that span; the observed 194 scheduled runs are about **10.6%** of those slots.

This is sufficient to say **the observed workflow history does not substantiate 30-minute detection cadence**, which the original workflow comments intend. It does NOT establish the cause (GitHub scheduler throttling, resource/usage limits, cancellations, history gaps or configuration changes must be investigated separately) or that site downtime occurred in unsampled gaps. Do not convert successful-run proportions into site availability.

## What this establishes about the proposed method

| Pilot question | Outcome |
| --- | --- |
| Does a chosen mutation survive an existing green test? | **YES:** the old monitor's six fixtures all passed after disabling forbidden-body protection |
| Can a cheaper, correct positive/negative pair reveal that blind spot? | **YES:** the new mixed-content invalid fixture rejected only by the correct implementation |
| Can the monitoring test distinguish successful customer-facing domain probes from failure of a comparison hostname? | **YES, by preserving per-check output:** five failures affected the comparison hostname while public apex/www probes passed |
| Can CI run and archive a small cross-project evidence contract? | **YES, for P2:** GitHub Actions artifact retrieved and independently copied with SHA-256 verification |
| Is the scheduled monitor actually sampling every 30 minutes? | **NOT ESTABLISHED:** recorded median 4.84 hours, requires root-cause analysis |
| Is the draft ASES methodology demonstrated across unrelated substrates? | **Partially:** P1 and P2 show useful discriminating checks, but no independent reviewer or longitudinal baseline |
| Is the entire historic CI corpus durably preserved? | **NO:** nine selected logs and 196 metadata records archived; other historic run logs and artifacts remain unverified |

This is the key comparative finding: a controlled negative/positive check in P2 detected **a weakness in the test instrument itself** that the existing six green self-tests concealed. The method added targeted discrimination at a measured small *execution* cost. It is not yet evidence that a heavyweight universal compliance scheme would add value.

## Recommended next small investigations

1. **Investigate missed scheduled-run slots**, inspecting repo and Actions scheduling/usage configuration before choosing any schedule or monitoring replacement. The stated 30-minute protection cannot currently be assumed.
2. **Decide what assurance the DNS Cloudflare membership check promises when IP ranges are missing.** Mark such an observation `INDETERMINATE`/degraded if the actual authorized claim requires membership proof; don't silently imply that passing the obsolete-IP check proves it.
3. **Strengthen existing monitor self-tests** with the paired mixed-content fixture, after review in its own minimal PR; the P2 research branch deliberately did not change production detector source.
4. **Separate comparison-hostname probe failures from apex outage alerts** in future incident handling, without weakening a claimed invariant.
5. **Independent reviewer exercise** using source-first P1/P2 packets, with reviewer identity, time and missing evidence recorded. This still cannot be claimed complete merely from this author's separate consistency check.
6. For rollout, design an export mechanism retaining **all** future eligible CI results independently, with archive-integrity checks and visible failure behavior; do not presume a local hash manifest alone proves archival.

**Acceptance status: DEFER.** Source-only or synthetic evidence does not authorize booking/payment, DNS, infrastructure, production workflow or policy changes.
